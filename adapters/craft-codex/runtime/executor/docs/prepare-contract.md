# Codex prepare contract v1

`craft-codex-executor --validate` is read-only and `--prepare` performs zero model calls. The input remains the typed original authority/lead/task selection handoff used by the patched Craft executor. `AcceptedResearch`, source digest, workspace/app binding, frozen build/check plan, external scenario, writable/protected roots, typed return routing and owner lease semantics are retained.

The handoff's `model` must select `backend_id: craft-codex-app-server-v1` and `permission_contract: codex-dynamic-bounded-v1`. `provider_manifest` is a hashed `codex-profile-v1` JSON reference. It contains one host CLI identity, one dedicated bounded server path/hash/version/source SHA/ToolPolicy tag/argv, `native-codex-home` auth mode, a secret-free MCP inventory hash, provider/model/effort, and `budget.usage_mode: audit-only`. It contains no API key, auth contents or copied profile. The profile itself is read and hash checked; auth files are left for the normal Codex host/profile.

`Budget.response_hard_cap` is always unsupported for this Codex profile, even when a profile self-declares `response_token_cap`. Only `response_token_cap: null` with `usage_mode: audit-only` is accepted; actual native usage, wall time and refinement limits are recorded/enforced. Aggregate `strict` remains unsupported. Missing or malformed usage is an execution failure/unknown, never zero usage.

The Codex profile's `auth.mcp_inventory` is a hashed JSON reference containing only a secret-free MCP-name inventory. The executor reads this inventory in memory and extracts all names under `mcp_servers`, `mcpServers` or `servers`; it never serializes or logs raw config/read responses. Before the dedicated Codex server child is spawned, every extracted server name gets an exact `-c mcp_servers.<name>.enabled=false` pair. The host server's own ToolPolicy is the authoritative startup and per-thread defense; this driver enumeration is an additional audit/argv consistency gate. Native skills/plugins/hooks and blocking native inventories are rejected at thread metadata admission; `request_user_input` is visible only as always-denied and is interrupted on request.


The Codex driver starts an owned app-server and an owned bounded MCP child. `thread/start` receives `ephemeral: true`, the exact model/effort selection, `environments: []`, and exactly six dynamic tools: `mcp__craft__build_files_list`, `mcp__craft__build_file_read`, `mcp__craft__build_file_write`, `mcp__craft__build_file_edit`, `mcp__craft__build_command_run`, and `mcp__craft__build_checklist`. No builtin filesystem/shell/REA/research/native tools, plugins, hooks, skills, code mode, extra MCP tools or model reroute are admitted.

The current development exchange is `initialize -> initialized -> thread/start -> turn/start -> dynamicToolCall/toolResult -> turn/completed`. The driver requires actual model identity and numeric input/output/total usage in terminal completion. Native event shapes not matching the typed contract fail closed until the isolated app-server fixture qualifies the exact 0.167.0-alpha.4.1 spelling.

Cancellation uses the owner identity marker and Codex `turn/interrupt`, then requires terminal turn state, explicit stdin shutdown, child exit, owned member emptiness and closed pipes. Unknown cleanup retains the owner lease and returns `blocked-cleanup`. The output is always candidate-only and original lead/Spec/primary authority remains responsible for acceptance and typed return routing.
