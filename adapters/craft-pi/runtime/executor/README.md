# Installer-owned portable executor

All production Rust and Cargo bytes are unchanged from FROZEN-SOURCE-MANIFEST.json. All meaningful tests, fixtures, examples and development helper source are retained. snapshot-origin.json records the original and portable file identities; documentation/test/helper transforms are not production changes.

Build/test through the installer packaging recipe in docs/craft-packaging.md. Tests require explicit CRAFT_TEST_NODE, CRAFT_TEST_ROOT and (executor) CRAFT_TEST_DRIVER/CRAFT_TEST_CARGO. There is no developer-machine tool fallback. Fixture binaries are built only with --features fixtures and never included as runtime binaries. Native qualification helpers are preserved development source, syntax checked only here; no live/provider/native qualification is claimed. They additionally require explicit CRAFT_GNU_BIN, CRAFT_PI_ENTRY, CRAFT_NATIVE_CSC and CRAFT_NATIVE_WORKSPACE where applicable, plus their reviewed external scenario inputs.

The project distributes its owned code under the MIT option of the unchanged dual-license declaration. LICENSE-MIT identifies our own project owner; upstream dependencies retain separate original notices.

# craft-pi-executor

Owned Rust integration for the patched Craft `RebuildRun` and the independent `pi-rpc-driver`. This crate is the application entry, public `pi` AgentAdapter and bounded MCP server. Craft retains the implementation/check/refine loop. There is no second coding loop, research capture, native Evidence import or default provider.

Development path dependencies intentionally point at adjacent `craft-pi-bridge` and `craft-anything-adapted`. Distributed executables have no such runtime dependency. `scripts/stage_build.py` reconstructs that relative source layout in a fresh staging directory using exact upstream commit `0326b4de8051f85a0f3139cd82f88f76911e6a35` plus ordered reviewed patches, builds sequentially, scans actual PE DLL imports and assembles installer-compatible native paths. The shared installer/reverse/official Pi/REA/Spec/desktop sources are untouched by this crate.

`entry-protocol.json` is the machine contract.

Production entry from an original R46 case uses `--validate /absolute/handoff.json` then `--prepare /absolute/handoff.json`, followed by `--run /absolute/owner-output/execution.json`. Prepare makes zero model calls. [The typed handoff contract](docs/prepare-contract.md) describes original case/scope/workitem/feature/spec/plan/tasks/acceptance references, the lead decision, task dependency selection, approved source, external observation/check plan and execution budgets. Original lead/Spec runner remain the authority; hashes and supplemental selection records never accept a task or upgrade evidence confidence.

A complete independent console example is supplied without NativeNotes or machine-specific runtime paths:

```text
cargo run --locked --offline --manifest-path /ABS/craft-pi-executor/Cargo.toml --example console_handoff -- /ABS/FRESH_CONSOLE_INPUTS /ABS/pi-rpc-driver.exe
/ABS/craft-pi-executor --validate /ABS/FRESH_CONSOLE_INPUTS/handoff.json
/ABS/craft-pi-executor --prepare /ABS/FRESH_CONSOLE_INPUTS/handoff.json
```

The low-level `ExecutionConfig::load` API remains available to protocol fixtures and internal tests. The production CLI `--run` path is stricter: it requires `execution.json` produced by `--prepare` and rejects a missing `handoff_context` before any Builder or provider work. There is no raw-policy production fallback. Prepared execution re-reads the original immutable handoff and original lead decision, reconstructs full policy/config through the same assembler mapping and rejects source/model/command/write-root/budget/layout/refinement changes even if callers refresh local policy/config/context hashes. The original external check plan and its generated copy are both hashed, then compared as typed plan data; harmless JSON formatting differences cannot change execution authority.

The example creates only explicitly labeled designed test documents/source/observations and a synthetic offline model definition; it does not qualify a provider or represent third-party/REA research. Replace the example inputs with the original case's real reviewed references and exact minimal target provider before a production `--run`. Configure explicit Node/Pi runtime environment as below; never put a credential value in the handoff. `console_handoff` creates a fresh directory and refuses overwrite. No need to run any NativeNotes preparation script.

Prepare supports an existing formal Workspace with its approved source hash, an explicitly empty new Workspace, or a link-free approved source copy into a new formal Workspace/app. It rejects task IDs absent from standard Spec checkbox T### records, uncompleted/mismatched dependencies, stale hashes, missing evidence/model permission or unreviewed target/scope/Spec changes before creating resources. For a new Workspace, `read_references` must be empty in v1; pre-stage exact reference files using an existing formal Workspace when the Builder needs file access to them. Instructions are explicitly reviewed and hashed.

Required missing-evidence/unsupported checks stop the Craft batch without another Builder research/refine turn. A typed `return_summary` names affected original tasks, check reason codes, original refs and the next authority (`original-primary`, `spec-runner` or `lead`). Bring missing facts back through the original route, obtain the same authority's updated refs/lead decision/selection and prepare a **new batch**; do not patch the old accepted records, tasks or runtime history. Scope/Spec mismatches are explicit input decisions, not guessed from user text. Implementation failures can refine within the original fixed plan. Cleanup unknown remains blocked-cleanup and retains its cause and source lease. Only check report v2 supports typed return routing; v1 diagnostic records are not accepted as typed proof.

Strict aggregate token/cost caps return `unsupported-budget` before any write. Audit-only aggregate mode records the coordinator's usage ref or explicit unknown reason, configured per-response maxTokens, hard wall/refinement limits and actual usage; it does not claim a hard total-cap platform.

`--version` and `--inspect` print JSON. Production `--run ABSOLUTE_PREPARED_EXECUTION_JSON` runs only an execution JSON emitted by `--prepare` and prints its JSON result. Exit 0 means candidate (or inspection); exit 1 means an executed failed/stopped/blocked run; exit 2 means admission/configuration/runtime failure. Candidate always contains `accepted: false`. Craft Ready/Finished/TurnDone alone never establishes success.

Production requires explicit `CRAFT_PI_NODE` and `CRAFT_PI_ENTRY` paths supplied by the installer entry, with an exact official Pi 1.5.0 version probe. Missing files/environment fail closed; there is no development-machine path fallback. The same binary's internal `mcp` subcommand requires an exact policy path/hash, workspace and fresh config root. It constructs `Engine::bounded_builder(Session::isolated(...), Arc<Policy>)`, attaches the formal workspace inbox, and serves only the six policy Build tools. Every actual call goes through the policy gate. No generic upstream MCP policy flag is invented.

Execution configuration uses deny-unknown-fields JSON and requires:

- `contract_version: 1`; `workspace` and explicit `create_workspace` boolean.
- `policy` / `policy_sha256`: accepted external research, current frozen check plan, original identity, source hash and explicit model permission.
- `driver` / `driver_sha256`: exact compiled RPC driver executable.
- `instructions` / `instructions_sha256`: reviewed literal instructions file.
- `provider_manifest`: `{ "path": "ABSOLUTE_PRIVATE_REVIEWED_MODELS_JSON", "sha256": "..." }`. Production requires this. Exactly one selected provider/model is admitted; target API/compat/reasoning/thinking mapping are preserved. `apiKey` must be `${ENV_NAME}`, that name must appear in `credential_env_keys`, and headers, literal credentials, extra providers/models/resources are refused. Builder `maxTokens` must be reviewed within 4096..8192 per response. The executor reads this supplied minimal resource, never personal profiles or auth/MCP configuration. It copies only this definition into each owned turn agent root; keep the run root inside the private helper's ACL-protected tree for private qualifications.
- `credential_env_keys`: names only, never values. The driver resolves required variables from its explicit child environment and fails if missing. Public bundles do not include provider resources or credentials.
- Fresh absolute `run_root`, absolute `stop_marker`, `message`, and bounded `max_refinements`.

Each turn explicitly sets the driver's typed `public_selection` to the exact provider/model/thinking triple already frozen and independently disclosed by the policy owner. This declares only selection metadata as public; it does not classify a credential value as non-secret or create a general control allowlist. The triple must exactly match the configured selection. Resource paths, run identities and other control roles retain the driver's collision refusal, and untrusted authoritative message/tool content remains redacted. The driver's default `None` behavior remains strict for callers that make no public selection declaration.

At least one required source build and one required external business scenario are mandatory. Current policy uses `BuildInvocation {command_index, artifacts}` with implementation `bounded-command-build-v1`, freezing the real command, app cwd/deadline and fresh output paths. Its owner check preserves prior outputs and records source/output hashes. An unknown/no-op toolchain cannot substitute for this receipt. Scenario v2 uses `direct-exec-v1`, `fresh-copy-v1`, an explicit runtime list and initial seeds; every attempt executes in a fresh copy. External observations use their actual namespace and remain unqualified as native REA claims. A bounded call policy does not turn Deep-derived inputs into a Clean Room result.

A cooperative source lease records raw owner PID, owner identity, accepted source/policy hashes and run root. The patched Craft source lease is additional. Unknown cleanup or lease persistence errors preserve ownership marks; there is no PID-only stale takeover. Within one Craft conversation, the next turn resumes only the exact header-verified session file reported by the driver. Cross-run session/history reuse is currently unsupported.

Stop handling notices the configured external marker, freezes the Craft owner through its cancellation token, atomically writes the current driver identity marker, allows bounded clear_queue/abort/idle/disposal, and only then permits hard cancellation. The Rust worker join, individual driver Job receipts, and an actual local descendant PID/creation observer are separate facts. Unobserved cleanup blocks candidate and retains the lease. This is trusted local-process handling, not an account sandbox, remote-service observer, port/business rollback guarantee or hostile-code isolation.

Results save the actual source hash and per-file before/after hash diff, real check results, external qualification/unknowns, authoritative model metadata and deduplicated main/nested usage. Missing optional upstream model/effort remains null/unknown. Public receipts exclude provider definition values and raw authoritative message bodies; stderr content is discarded with byte counts. There is no hard aggregate token/cost enforcement: wall/refinement budgets are enforced and actual usage is audited. Estimated cost is not actual billing.

Build tools: installed GNU Rust/cargo 1.99 and the explicit MinGW linker. `python scripts/build_job.py check` performs a locked offline check with a separate target directory; `python scripts/build_job.py test` first builds the exact driver source in an owned target directory, then compiles/runs fixture tests serially. Tests use Node + a scripted offline Pi JS entry and invoke the actual bounded MCP executable through the frozen driver. This exercises the real Node launch, new/resumed session and Craft/driver/MCP loop without a provider. The optional direct-executable offline peer is a separate test fixture, not a production fallback. `scripts/debug_fake.py` preserves the minimal extended-Windows-path Node reproduction used before the driver's canonical-identity/Node-argv fix; the full driver regression is authoritative. See the integration report for current results and pending dependency reviews.

The staging script accepts explicit source/patch/compiler directories; run `python scripts/stage_build.py --help` for its required inputs. Final binaries are `bin/craft-pi-executor.exe` and `bin/pi-rpc-driver.exe`, with only actually imported non-system DLLs included. Full staging, installer verification, independent acceptance, real provider/native callback, license inventory and deployment qualification are separate gates. Nothing in this README claims a full product result.
