# Installer-owned portable bridge

All production Rust and Cargo bytes are unchanged from FROZEN-SOURCE-MANIFEST.json. All meaningful tests, fixtures, examples and development helper source are retained. snapshot-origin.json records the original and portable file identities; documentation/test/helper transforms are not production changes.

Build/test through the installer packaging recipe in docs/craft-packaging.md. Tests require explicit CRAFT_TEST_NODE, CRAFT_TEST_ROOT and (executor) CRAFT_TEST_DRIVER/CRAFT_TEST_CARGO. There is no developer-machine tool fallback. Fixture binaries are built only with --features fixtures and never included as runtime binaries. Native qualification helpers are preserved development source, syntax checked only here; no live/provider/native qualification is claimed. They additionally require explicit CRAFT_GNU_BIN, CRAFT_PI_ENTRY, CRAFT_NATIVE_CSC and CRAFT_NATIVE_WORKSPACE where applicable, plus their reviewed external scenario inputs.

The project distributes its owned code under the MIT option of the unchanged dual-license declaration. LICENSE-MIT identifies our own project owner; upstream dependencies retain separate original notices.

## Explicit input and output contract

Invocation is either `pi-rpc-driver --config /absolute/config.json` or `pi-rpc-driver /absolute/config.json`. Unknown arguments fail. The driver reads one UTF-8 task from stdin until EOF, with a 1 MiB bound and `input_ms` deadline. The config is a separate JSON file, never inferred from task content. `config.example.json` documents the serialized shape; its example directories and MCP identifier must be replaced/prepared by the execution owner. The example is not runtime qualification.

All config objects reject unknown fields. `credential_env_keys` defaults to an empty list for existing JSON configs. It contains variable names only, for example `["CRAFT_PI_PROVIDER_API_KEY"]`; the executor sets those variables on the driver process and references the same names from its isolated models configuration. The driver resolves only these names and passes them to Pi in addition to infrastructure variables. No credential values belong in config, example files or reports. Lists are limited to 32 unique names (case-insensitive duplicate/reserved checks); names must match `[A-Za-z_][A-Za-z0-9_]*` and be at most 128 bytes. PI/runtime-loader/resource-selection variables and PATH/OS/temp/locale/home overrides are reserved. Invalid/reserved names fail explicitly; a missing or empty required value returns `credential_env_missing` before spawning Pi, with no provider/model fallback. Malformed names are not echoed in errors. Rust struct literal callers must supply `credential_env_keys: vec![]` or the explicit names; omission compatibility applies to JSON deserialization.

`public_selection` defaults to `None` when absent or `null`. It is an optional, explicit policy-owner declaration that the configured provider/model/thinking identifiers are independently public; it is never a declaration about credential values. Rust callers import `config::Selection` and supply `public_selection: None` or `Some(Selection { provider, model, thinking })`. All three string fields are required, unknown declaration fields are rejected, and each must equal its configured counterpart exactly; partial, boolean, mismatched and arbitrary-control declarations fail with `invalid_config`. Existing JSON configs retain strict collision refusal. Rust struct literals must add the new field.

With a valid declaration, only selection-role collisions are admitted. Known typed provider/model/thinking metadata and the exact model identity in `set_model.data.id` / `get_state.data.model.id` retain the independently public spelling. Normal response/session/run/tool IDs, schema and paths keep their original collision guards. No prefix, wildcard or arbitrary metadata allowlist exists. An undeclared responseModel string is treated as untrusted and redacted before exposure; the protocol parser still independently requires authoritative identities to agree. The config declaration and the controlled preflight evidence record the selection exception without reporting which injected value matched which selector.

Values must be UTF-8, at most 16 KiB each and 64 KiB total, so matching state remains bounded. Injected values are matched literally and in their exact JSON-escaped spelling. **With credentials present, output is deliberately reduced:** message_update/text/thinking/toolcall deltas, message_start, tool partial updates, turn/agent snapshots and unknown payloads become content-free `bridge_progress` records. Tool starts retain identity with empty args. Only authoritative completed messages and tool results expose text; all text parts in that complete content are joined before matching, trailing matching prefixes are masked, and non-text/thinking/opaque payloads are omitted. This prevents separate delta/part records from reconstructing a credential before the final message arrives. If no credentials are configured, the original Pi event passthrough remains unchanged.

Protocol object keys and control/identity metadata are never blindly rewritten. By default, known schema/config/tool/model/run/turn conflicts fail before spawn with `credential_control_conflict`; the strictly matching `public_selection` declaration admits only the selection role as described above. Newly observed session/response/tool identities remain checked before their record is emitted, and collisions fail with that same stable code. A refusal preserves the error schema even for a short value such as `type`, so literal redaction of schema spelling is intentionally not claimed on that path. It never produces a successful result with silently changed IDs, hashes or provider identity. Returned Report failure details/final content are sanitized before return or Debug use, while stable failure codes remain unchanged. Stderr retains a byte-level matcher across read chunks and masks an EOF-truncated matching prefix. The private cloned matcher has opaque Debug. This is exact plaintext/JSON-spelling redaction, not arbitrary-encoding exfiltration prevention or OS sandboxing. Injected credential values remain protected in untrusted content and diagnostics; independently declared public selection identifiers remain public metadata. This deliberately does not claim that an equivalent short string can never occur anywhere in the output bytes.

All resource paths are absolute, directories must already exist, and task/agent/session roots must not overlap. `session_path: null` means a new session; an explicit file means resume that exact existing file. No latest-session search, history repair or silently fresh replacement is performed. Supported executable prefixes are a direct executable with empty `pi.argv`, or Node/Bun with exactly one absolute JS entry script. Shell wrappers, SSH and arbitrary extra Pi arguments are rejected. Instructions are literal reviewed text; existing-file-path ambiguity is rejected. Selected MCP names must be exact `mcp__...` identifiers, with no patterns, discovery tools or native tools.

Windows canonical identities may use a verbatim prefix, but Node 24.20 cannot reliably consume that spelling for its entry argv. The driver now derives ordinary drive/UNC absolute launch spellings using parsed Windows path prefixes, then canonicalizes both spellings and requires equality before use. Device/unsupported namespaces are refused; blind prefix trimming is not used. Program, JS entry argv, cwd, agent/session environment, session-dir and exact resume args use compatible native spellings; stored identities and session/root checks remain canonical. Instructions stay literal reviewed text. `tests/fixtures/fake_pi_node.cjs` was executed using the actual `the explicitly supplied local tool path` for new/resume RPC and records entry/cwd/env/session spellings plus instruction equality. The fixture uses only Node built-ins, not Pi/provider resources. UNC prefix conversion is tested lexically; a live network UNC share has not been exercised.

`cancel` contains `marker`, `run_id`, `turn_id`, `generation` and `token` (identity is flattened in JSON). The owner supplies fresh unpredictable IDs/token; syntax validation is not proof of randomness. To cancel, atomically write the following object to the configured marker path using an owner-local temporary file and rename:

```json
{
  "run_id": "the-current-run-id",
  "turn_id": "the-current-turn-id",
  "generation": 1,
  "token": "the-current-token"
}
```

The marker is limited to 4 KiB. A different valid identity is stale and ignored; malformed/unreadable control input fails explicitly. Matching cancellation emits `bridge_cancel_ack` without the token. The driver waits for a correlated `clear_queue` success before sending `abort`, waits for its documented idle response, closes stdin, then waits for exit. Grace, shutdown and hard-kill deadlines are separate finite stages. `turn_ms` covers the RPC handshake and model turn; input, teardown and finite output-write waits are additional stages. A controller must budget their sum.

Stdout is LF JSONL. Pi records remain Pi records; `bridge_session`, `bridge_failure`, `bridge_complete`, `bridge_cancel_ack`, `bridge_ui_denied` and `bridge_stderr` are explicitly our own namespace. A Pi child cannot inject `bridge_*` records. Stderr drains independently and is emitted as byte arrays after the explicit-credential byte filter, preserving other bytes without confusing diagnostics with protocol or splitting multibyte text. Sensitive matches become `[REDACTED]`; stderr chunks may be delayed/repartitioned to protect a match spanning read boundaries. Stdout has a 1 MiB record and 16 MiB stream limit; stderr has a separate 16 MiB limit. Both are drained after a limit failure while teardown proceeds. Bounds also cover the inter-thread queues and session validation. Persisted session JSONL is currently limited to 16 MiB; large-history handling is a future explicit contract change.

Argument/config/input failures also use the bounded output writer: preflight details are capped at 4096 characters, each preflight record write waits at most 250ms, and the CLI exits even if the receiving pipe stays open without reading. A blocked sink can therefore prevent delivery, but cannot hold the preflight process indefinitely.

`bridge_failure` carries `code` and `detail`. `bridge_complete` carries `success`, cleanup facts, Pi exit status, settled status, final assistant message, deduplicated main-model usage, separate nested tool usage and cancellation acknowledgements. Exit 0 means the driver verified the protocol and owned cleanup; exit 1 means an executed turn failed; exit 2 means argument/config/task ingestion failed before the child started. A closed output sink may prevent any structured record from being delivered, so the receiver must also inspect process exit and a missing completion record.

## Protocol and session behavior

The child starts with explicit model/provider/thinking/sessionDir and isolation flags: RPC, no trust-gated project resources, no context files, no skills/templates/extensions, offline catalogs, explicit `builtin:mcp`, exact MCP tool selection and reviewed instructions. The environment is cleared except infrastructure PATH/OS/temp/locale variables, the explicitly set owned Pi directories/offline flag, and credentials named by `credential_env_keys`. Unlisted credentials and inherited PI selection are not copied. This does not implement an OS sandbox or a server-side MCP permission gate.

Readers start before commands. The correlated sequence is `set_model` → `set_thinking_level` → `get_state` → `prompt`. `get_state` must report the expected exact triple, idle state, empty queue and owned absolute session file. `prompt` must report `started`; `queued` and `handled` fail and enter cancellation. Extension dialogs receive an explicit cancelled response, are recorded and fail the task. Notifications do not require answers.

For resume, the entire existing JSONL is framed/parsed before launch; header v3/id/cwd are checked against state before prompting. For **new** sessions, official Pi 1.5.0 keeps setup-only entries in memory and creates its JSONL only at the first user/assistant message (`dist/core/session-manager.js`, `_hasConversation`/`_persist`). Therefore the new path's real parent/root and state identity are checked before prompt. During active events, an empty just-created file, a partial header or an incomplete appended record is not treated as corrupt. After `agent_settled`, Pi stdin is closed and disposal/process exit is awaited; then the full JSONL and header/id/cwd are strictly checked, and only then is the new `bridge_session` emitted with `headerVerified: true`. A pre-existing new-session file is refused. Resume still validates before prompt and again after disposal. This avoids racing create/append writes while preserving strict rejection of truncated or malformed history at the stable exit boundary; no native header is fabricated.

Every authoritative assistant must report the selected provider/model. Official assistant `thinkingLevel` and `providerThinkingLevel` fields are optional: absence remains absent/unknown in emitted and returned metadata, while any supplied value must agree with the configured level. Startup `set_model`/`set_thinking_level`/`get_state` still strictly verifies the requested selection; it is not proof of unreported provider-native effort. Optional responseModel must agree when present. This strict first version supports exact physical identities; virtual model routing and provider-specific effort aliases need explicit later qualification. `message_end.message` is authoritative; `error`, `aborted`, `length`, `pending` and unresolved `deferred` fail. `toolUse` may precede another assistant response; the final authoritative response must be `stop`. Usage is counted once per completed assistant response (provider response ID, or exact completed message), never by summing cumulative streaming snapshots or `turn_end`. Tool nested usage is separate. `agent_end` does not complete the turn. Only non-aborted `agent_settled`, no active tools, successful final and orderly child exit satisfy the protocol. Run events after settled and unexpected tool names fail.

## Craft integration seam

The next integration task owns the actual implementation of Craft's `AgentAdapter` and `AgentAdapters::register`/`RunOptions.adapters`. This crate does not pretend its helper is already registered in the upstream product.

- `adapter::PiRpcAdapter::load` loads the explicit config and driver path. `invocation` returns `Launch { program, args, stdin_text, cwd, agent_dir }`; it rejects SSH, extra args and question mode. `plain_fallback()` is false; `prompt_on_stdin()` is true; `folder_var()` is `PI_CODING_AGENT_DIR`.
- `parser::BridgeParser::parse` produces `AdapterEvent::{Session, TextDelta, ToolStarted, ToolFinished, Failure, Completed}`. Map these to Craft parser/session/run_session fields and its existing agent events. Preserve final metadata and usage from `bridge_complete`. When credential references are configured, raw content deltas are withheld; consumers must display authoritative `message_end`/`bridge_complete.finalMessage` content or content-free progress rather than require TextDelta delivery.
- `PiRpcAdapter::session_file` returns only the exact bridge-reported owned file and rechecks header id/cwd. For continuation, the execution owner writes the next explicit config with that `session_path`, a fresh turn identity and the accepted contract. No implicit restoration/copying of a missing session occurs.
- `BridgeParser::successful(driver_exit)` requires driver exit 0, a verified session, completion success/verified cleanup and no bridge failure. Craft's existing runner should emit its one `TurnDone`; do not produce another for every `agent_end` or treat `TurnDone` as success.
- `driver::run(Config, task, writer) -> Report` supports direct embedding/tests with the same state machine. The output sink must have finite writes for leak-free library use. A permanently blocked arbitrary `Write` may retain its bounded writer thread; it cannot prevent child teardown. The CLI exits the process after returning.

P0's task/source hash contract, exclusive source/session ownership, acceptedResearch, exact tool-service list/call/argument gates, and the actual Craft trait impl remain outside this crate. The caller must guarantee a single owner and refuse another writer while cleanup is unknown. No shared-source or source-lease framework has been added here.

## Cleanup qualification and remaining gates

Windows creates Pi **suspended**, assigns it to a new Job with kill-on-close and no breakaway, then resumes the single initial thread. Teardown queries the actual Job's `ActiveProcesses` plus root exit and pipe EOF; only observed emptiness is `verified`. Assignment/query/teardown failures are not reported as verified. Startup failures after process creation retain their actual cleanup facts. Snapshot/OpenThread/Resume failures terminate the suspended/owned process and wait for bounded root/Job observation; an unconfirmed result is `unknown`, never `not_started`. Assignment failure likewise tracks the suspended child's exit. Fixture-only fault injection has no CLI/config/environment entry point. Tests exercise these startup failures, unconfirmed cleanup, cooperative cancellation, a nonresponsive process, surviving descendants and direct termination of the driver (Job handle closure).

Unix starts an owned process group and kills only that group. Group emptiness is observed, but setsid/setpgid descendants can escape. Without a cgroup/external descendant observer, overall cleanup is deliberately `unknown`, the run fails with `cleanup_unknown` after otherwise successful protocol, and an owner must block replacement work. Unix code was not built or executed on this Windows host. This is a documented platform admission gate, not a claim of cross-platform production readiness.

Job cleanup covers processes contained in this Job, not remote services, pre-existing external processes, business rollback, port side effects, a service broker that launched outside the Job, or hostile code under the same account. There is no ACL/account/VM isolation claim.

Real provider qualification is **not performed by this Worker**. Isolated models configuration, explicitly named credential variables and the restricted MCP service are owned by the executor/runtime task; P1 does not copy personal auth resources or add provider-extension CLI injection. Automatic extensions remain disabled and arbitrary `-e` args remain forbidden. Missing executable returns `runtime_unavailable`; unavailable provider/configured model returns command/assistant failure rather than fallback. Enabling the real provider requires the next explicit integration/resource contract, not copying personal resources or weakening the argv gate. `get_state` and assistant metadata cannot authenticate a gateway's hidden upstream.

P1 protocol results do not establish P2 integration, business implementation/check/refine success, P3 UI/persistence equivalence, installer activation, product readiness, performance benefit, or deployment qualification. Those remain separate gates.
