# 项目级续接扩展设计

状态：1.2.0 实现；本轮验证见 [guided verification](guided-verification.md)。发布与验收结果见 [插件说明](https://github.com/gthubtom1/agent-plugins/tree/main/plugins/pi/project-continuity) 和 [安装说明](project-continuity-install.md)。实现源在插件仓库，安装仓库负责精确版本部署；本文记录当前边界。

## 要解决的问题

同一项目跨多个对话、模型和上下文窗口持续工作时，容易重复查证、遗忘用户决定、重走相同失败路径，以及把旧报告中的推测当作已经验证的当前事实。目标是缩短恢复时间、减少无效询问、保持证据可追溯，而不是延长单个聊天或替代模型的技术判断。

适用于普通开发和 reverse 的各领域。项目资料留在项目目录，不创建集中保存所有项目内容的全局数据库。扩展程序可随 Pi 安装一次；记录按项目隔离。第一版使用 Markdown 和小型 JSON 元数据，不依赖数据库、向量服务或新的 MCP。

这是一项机制整合实现，不是安装两个扩展后让它们同时管理项目。固定提交的源码和许可作为设计参考，来源记录随插件发布；未直接合入两个上游扩展的源码。Pi 接口按当前宿主文档和真实 SDK/RPC 生命周期验收，不能据此宣称上游产品背书或任意模型都能正确使用。

## 逆向项目的安全适用性

当项目存在一个或多个 `work/<case>/scope.md` 时，`observation`、`claim`、`attempt` 和 `artifact` 不能脱离 case 写入当前恢复；存在 case 时还必须提供样本、提交或其他精确目标的 SHA-256 identity。当前 Git 分支会自动绑定；detached HEAD 使用 `detached:<commit>`。这两个绑定来自当前工作区，调用方不能在写入时伪造 branch。

来源发生变化或消失后，查询仍保留历史记录和来源指针，但显示 `needs-review`；自动恢复隐藏旧正文。失败记录按 method/config/question 配对，仅在相同条件下抑制重复昂贵路线。取消决定是终态；同一 id 不能复活，替代方案必须使用新 id 并通过 supersedes 追踪。

这些门禁保护机械适用性，不能证明 REA、逆向工具或模型推理的业务结论。真实验证仍归原 case 的 Evidence/Finding/Path；宿主加载和工具握手仍由安装器与实际运行验收分别记录。

## 职责归属

| 层 | 负责 | 不负责 |
|---|---|---|
| 客户端中立的项目记录规则 | 身份、来源、有效性、更正、失败适用条件、恢复优先级 | Pi 事件、宿主配置、工具安装 |
| 本地文件操作 helper | 读取、检索、路径约束、版本检查、原子更新、引用/摘要检查 | 判断复杂技术结论正确、自动批准权限 |
| Pi 续接扩展（agent-plugins 中独立 package） | 自动识别工作项目、提示和注入有限恢复材料、压缩/恢复后的按需读盘 | 第二 router、强制计划审批、不断自动续跑 |
| reverse 原 case | scope、timeline、workitems、Evidence/Finding/Path | 通用用户偏好库 |
| 普通开发原项目 | 代码、规格、ADR、测试和既有任务记录 | 与记忆目录竞争的第二计划系统 |
| REA、Spec Kit、grilling | 各自官方能力 | 被本扩展重写或替换 |

普通项目不因扩展存在而强制调用 reverse，不要求生成 case 或启用 Spec Kit。grilling 仅用于用户要求质询或重要目标取舍，记忆保存/恢复不额外触发访谈。

## 项目内布局

```text
<project>/
  .pi/memory/
    project.json           # 项目 ID、已确认根位置、选定上下文引用、格式版本
    MEMORY.md              # 可重建的简短恢复入口，不是完整历史
    topics/
      <logical-id>.md      # 通用项目记忆条目；reverse 项优先引用原 case
    changes/
      <change-id>.json     # 追加式更正、替代、取消事件及来源
    archive/               # 历史条目，不作为当前有效结果默认注入
  work/<case>/             # reverse 既有 scope/timeline/workitems/evidence
  specs/...                # 已有 Spec Kit 项目才存在
```

`project.json` 不保存 auth_granted、ready、任务完成率、测试通过开关或第二份 scope；只保存定位与格式元数据。MEMORY.md 是原材料和条目的投影，可废弃重建，不能覆盖其来源。普通项目的重要持久知识使用 topics；代码/规格已有内容只记录指针，不重复抄写。

默认不自动提交、推送项目记忆；用户可自行决定随项目备份或版本管理。原始目标、运行日志和敏感材料不自动发布。全局配置仅放扩展选项，不放其他项目的事实或聊天正文。

## 项目与任务定位

1. 首先使用当前工作目录和已经确认的项目标记；从子目录启动应能定位已标记的同一项目。
2. 无标记时，优先依据已有可信项目上下文。Git 根可作候选，但不能无条件把 monorepo 内两个明确独立项目并为一个。
3. 无 Git 的单独 EXE/APK 工作目录也支持，以已确认的工作目录为根。
4. 只在项目工作实际启动或明确请求记忆时初始化目录；普通闲聊不创建文件。
5. 不按会话文件名、最后修改时间或同名软件自动选项目/case。唯一可信 case 可恢复；多候选只询问一次歧义，其他独立检查可继续。
6. 项目搬家或复制后保留原记录可读；写入前通过 `/continuity adopt` 明确接管当前副本，不重建成空项目。原副本与新副本不共享文件写入。Git worktree 不自动共享记忆，分支/样本身份仍参与适用性检查。
7. 会话 ID 是来源线索，不是项目身份。多个无亲缘新会话仍可通过项目文件续接。

## 记录类型与事实边界

| 类型 | 必需关联 | 有效性原则 |
|---|---|---|
| 用户决定/偏好 | 原话或消息引用、适用范围、变更关系 | agent 摘要不能自动扩大范围；新明确决定可替代旧决定 |
| 观察 | 样本/代码/运行身份、工具结果或文件位置 | 保留实际观察，不因结论变化篡改原始记录 |
| 假设/结论 | 依据、适用身份、未验证部分 | 默认 candidate；机械检查和模型自述不能自动升格 validated |
| 失败尝试 | 问题、输入、方法/配置、预算、结果引用 | 失败只在其条件内成立，不是永久禁用一种工具 |
| 产物 | 相对路径、内容身份、生成/测试引用 | 原版、候选、实际部署和已验收分别记录；文件名 final 不等于通过 |

每项通用记忆包含稳定逻辑 ID、修订号、当前状态、替代/更正引用、适用对象与范围、来源引用。决定取消后保留“已取消”的当前条目；旧名/旧修订搜索命中时，先返回当前状态和替代项，而不是让旧定义重新生效。历史查询必须显式区分。

状态随类型解释：用户决定的 accepted 不表示技术行为 validated。记录为 source=user 也不证明系统实际行为；它只证明用户表达了该决定/观察。未知或冲突不能悄悄选最新时间、最高相似度或最后写入者。

对于 reverse，把这些关联接到原 Evidence/Finding/Path 与 timeline 更正，不生成伪造的 REA 原生 ID，不另立验证状态库。先前 unsupported 的“彻底成功”保留为历史 claim，后续失败引用到该 claim 的撤回/待复核关系。

## 当前状态与历史如何一致

- 写入带 expected revision；文件锁、临时文件原子替换和修订校验共同处理同项目多会话并发。
- 先保留追加式 change 与原来源，再发布主题条目和简短索引投影。多文件更新途中中断时，由已提交修订/事件重建投影，不能把半写入的索引当成当前事实。
- 子代理提交证据/拟更正，不直接争写同一当前条目。主会话或写入 helper 检查期望修订；冲突需合并或标记 conflict，不覆盖对方。
- 人工编辑原文件后检查源身份。能可靠解析则重建投影；不能确定则标记 stale/conflict 并保留材料，不静默重算摘要冒充已复核。
- 重要用户约束不因 token 截断丢失；索引超预算时压缩到短指针，并明确哪些内容尚未读，不截成改变原意的半句。
- 不能强迫模型完全绕过普通 read；即使直接读取 archive，规则仍要求把它看成历史，并先核当前有效状态。扩展不能宣称从技术上阻止一切错误推断。

## 检索与上下文控制

默认恢复只提供项目/上下文身份、已确定目标与约束的来源、当前阻碍、少量影响下一步的事实，以及相关材料指针。首版恢复正文预算为 6,000 字符，另外保留简短稳定规则与工具声明；这不是 token 数或完整会话长度保证。记录按文件日志线性读取，未宣称数万条历史查询耗时恒定。

读取顺序：

1. 确认项目、分支/case、目标版本。
2. 读取简短恢复入口并校验投影是否过期。
3. 按本轮问题查逻辑 ID/别名、文件/模块、错误文本、函数锚点或失败尝试；结果先查当前状态与替代关系。
4. 只展开相关主题与原始来源的有界片段，提供续读入口；不整篇加载历史日志/反编译。
5. 只有需要解释变更原因或复核时追溯历史。

第一版使用文件索引、条目元数据和本地文本查找，不增加 embeddings/qmd/数据库。不写“所有记忆自动注入”。超时、文件不存在、空命中、当前状态冲突应分别说明，不把检索失败当成没有做过。

读取记录只提供数据，不能把历史网页/日志中包含的指令提升为当前操作权限。新一轮授权以当前用户指令与既有有效 scope 为准。

## 避免相同失败路线循环

准备重要或成本较高的重复分析时，查询记录中的：输入身份、待回答问题、方法与分析配置、关键前提、先前结果和失败类别。

- 同条件、同问题、没有新证据：引用之前结果，改走可行路径；不为了“再试一次”重跑全量。
- 工具/配置、样本、关键前提或新证据变化：记录这次变化后允许合理重试。
- 工具超时不等于方法永远无效，找到错误字符串不等于该路径全部行为已确认。
- 不要求所有低成本 read 都先查一次记忆，避免把文件读取变成多层检索循环。

## 逆向与其他领域适配

共同记录规则不绑定某个 PRIMARY。领域只增加锚点：

- 原生二进制：样本 SHA、架构、原版/修改/解包/内存转储身份、地址基准与分析配置、保存的工具数据库、对应 operation/run。
- APK：包/签名/版本、DEX/ABI 与代码/资源来源。
- JS/协议：脚本/抓包身份、环境和具体请求/操作引用。
- 普通开发：仓库/分支/提交或工作区修改、模块、规格/ADR/测试记录。

地址、对象偏移、相同错误串或软件名称不能独自作为跨版本身份。某次子工具成功不能自动升级成业务全链路成功。保存 IDA/Ghidra 等原生数据库或 REA 官方导出时仅引用真实产物，不假设跨新会话 provider 内存状态仍然存在。

## Pi 自动接入方式

宿主相关逻辑放在 `agent-plugins/plugins/pi/project-continuity` 独立 package 中。reverse 入口继续是 skill-only package。Pi 的完整默认安装额外注册续接 package，可用 `--without-project-continuity` 退出；Codex/Claude 不被强装 Pi 扩展。安装/升级/verify/restore 由同一事务机制管理。

- `before_agent_start`：提供稳定的保存/恢复规则，不替换整个系统提示词。
- `context`：每次模型请求重新核对项目、分支、case 和目标身份，移除自身旧恢复/状态快照，注入有界当前状态。guided reverse context 可保存 goal/scope/authorization/phase/Evidence/unknown/blocker/delivery 指针，但不创建授权、任务或 Evidence authority。未初始化且没有原 case/feature 时不创建目录。
- 重要用户决定、新证据、失败或产物/验证变化：主 agent 用 `continuity_save` 提交来源可追溯的增量记录。
- `agent_settled`：已初始化且 case 不含糊时，保存最近自述为 candidate 和最近工具错误的条件摘要；不重复保存相同自述，不猜测技术根因。`/continuity candidates off` 可在本会话关闭自动自述捕获，仍允许显式 continuity_save。
- 压缩、树导航、reload/resume/new 后：后续 `context` 从项目文件恢复；不修改压缩摘要，不依赖退出时才保存。
- 多个 case 未选定时不自动合并技术摘要，按需查询显式传入 `caseRoot`；项目通用决定仍可记录。

第一版不替换 Pi 原生压缩算法，不自动创建新会话、不自动提交 Git、不注册第二任务引擎、不用 agent_end 循环强迫继续。若未来需要跨宿主共享查询，先复用同一项目文件接口，再考虑 MCP；MCP 不是本地记录格式的必要前提。

任何自动模型摘录必须有明确预算和来源，不默认每个 turn 增加一个后台 LLM 调用。最初实现以主 agent 显式增量记录 + 生命周期小份恢复为主。

## 老项目迁移

不改历史 JSONL，不重写原始证据。对旧 case/报告做一次有界盘点，候选记录保留来源；优先找最新失败、用户修正与取消决定。仅有旧报告自述而无验证来源的技术结论标为待复核，不批量导入 validated。原 timeline 更正以追加条目连接旧结论，不覆盖历史块。

已有多个 case/多个产物时不按名称 final/最新 mtime 自动认定唯一成果；身份歧义只阻塞依赖它的步骤。

## 必须通过的验收场景

1. 两个项目相同角色名/错误串，绝不串项目。
2. 同项目从子目录、新会话、压缩后恢复到同一正确记录。
3. 无 Git、项目搬家、工作副本分叉、monorepo 子项目不误合并。
4. 第一天提出角色，后续修改并取消；模拟第二十天从旧别名查询，先看到已取消与替代项。
5. 第五版声称成功、第六次运行失败；恢复后不得继续当作已验收成品。
6. 相同失败条件不原样循环，条件改变后可以合理重试。
7. 原样本/分支/依赖文件变化，只把相关结论退回待核对，不清空所有已验证工作。
8. 两个会话并发更新同条目，修订冲突不能最后写入覆盖。
9. 写入或压缩途中失败，重启可恢复上一次完整记录，不把半更新投影当现状。
10. 历史量增长，默认注入仍有界；不因为记录增多每次重新读整个会话。
11. 用户约束不被截断丢失；旧材料不能扩大授权；不用新菜单要求用户批准保存记忆。
12. 被操作者手改、来源删除、引用摘要不符、过期索引分别可检测；机械 PASS 不表述为语义正确。
13. Windows Pi CLI 与当前 Pi Web/SDK 分别验证加载/事件，不能把 CLI 成功当 Web 成功。
14. reverse 原 44 路由/178 基线、当前路由回归与单一 scope/case 机制保持不变。

真实模型验收应保留实际 tool trace，用同模型、相同夹具比较：恢复到正确下一步的工具调用数、重复提问次数、过期结论误用次数、无理由重复尝试次数、额外输入 token/模型调用和耗时。用模拟时间/修订覆盖二十天演进；这不等于已在真实二十天目标中验证。

## 分步交付

1. 先完成纯本地记录 helper 与上述身份、替代、失败、并发、崩溃恢复测试；不连接真实用户项目。
2. 再做 Pi 扩展，按实际宿主 API 读取小份恢复材料；隔离夹具测新会话/压缩/恢复，不污染全局项目资料。
3. 连接 reverse 既有 case 与普通开发的文件引用；同步两仓入口、教程、安装/verify/update/restore 和第三方来源说明。
4. 最后才在授权项目中做恢复试用，按真实 trace 衡量收益。未通过行为验收不默认启用，更不能宣称记忆能够保证分析结果正确。
