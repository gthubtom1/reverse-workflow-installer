# 日常使用、首次验收与成果追版

安装器完成的是组件、配置和项目资源的安装；真正使用前还要按 [安装后快速开始](quick-start.md) 完成 `verify`、`accept`、宿主重启和一次对话冒烟测试。`installed: true` 只代表安装事务成功，不代表模型已经选择了 reverse-workflow。

如果你是零基础，先看 [Reverse 工作流手册里的零基础一键开始](reverse-workflow-playbook.md#零基础一键开始)。把目标放到当前对话工作目录根目录后，复制模板即可开始；后续由智能体在已授权范围内连续推进；只有需要你取舍目标、补充授权或材料时才提问。

安装后从独立成果项目启动指定 Pi/Codex 配置。专业任务优先显式使用 `/skill:reverse-workflow`，让智能体先读取组合入口和本机 receipt，再读 RULES、原 master-route 和 PRIMARY。REA 由 PRIMARY 在需要时调用，Spec Kit 用于成果项目的规格、计划和任务。Pi 仅在明确请求质询或存在重要目标取舍时使用 `grilling`，也可以开工时澄清目标；常规事实核查和既定方案内实施自动推进。

如果你想专门质询尚未确认的方案，可以说（可选）：

```text
现在先不要实施。使用 grilling 审查当前方案；需要文件、字节或工具才能回答的事实先自行查证，只把需要我决定的方案分叉列出来，等我确认共识。
```

达成共识后再说：

```text
我们已经达成共识。按确认的范围实施，完成后重新验证原版与产物，并报告失败项和 unknown。
```

可以直接说：

- “分析这个程序，把 X 功能复刻成独立项目，完成后和原版对比。先说明范围和 unknown。”
- “继续上次项目。读取旧 case、证据和当前 feature/tasks 后继续。”
- “现在做到哪里？分别报告已观察、推断、未知和已实测的功能。”
- “只验证这次实现和原版是否一致，保留失败输出和未执行项。”
- “到网上补充完善知识库，先定位 reverse 的原生维护说明，按已授权模块逐批复核来源。”

Pi 未自动读取入口时可用 `/skill:reverse-workflow` 或短 `/reverse-workflow` prompt。新对话与只读检查模板见 [安装后快速开始](quick-start.md)；独立实现使用同页的 [完整复刻复制模板](quick-start.md#需要独立复刻项目时)。纯分析可在报告结束；实现则走原生 Spec 全流程，默认普通 Worker，只有原 runner 为合格批次选择 Craft 才切后端。缺证回原 PRIMARY、代码缺陷预算内 refine、规格/范围回 runner/lead，接收后继续原 tasks/converge 与独立验收；短分支图见 [工作流手册](reverse-workflow-playbook.md#独立实现与源码恢复)。Codex 在 `CODEX_HOME/skills/reverse-workflow` 发现全局入口；选择成果项目时也可使用项目 `.agents/skills/reverse-workflow` 便携桥接，通过 receipt 指向现有 reverse 插件入口；不必把工作目录改成工具仓库。

追随产品 1.0→1.1 时说：

> 这个项目上游更新到 1.1 了，沿用我们的实现和界面，帮我跟随更新并验证。优先恢复这个项目的旧 case，不要另起一个不相干项目。

智能体应从原项目恢复旧上游 O、我方成果 C、新上游 N 的身份和材料。调查 O→N 的变化，复核 C 中我方设计对 N 是否仍适用；保留我方界面、品牌、构建和用户明确选择的差异。只把本轮选定的新功能放入新规格；缺旧材料、多个候选或身份不符时明确报告，不能按文件名盲合并。

旧版证据和通过记录保持原样，不能充当新版通过证据。变化的需求/obligation、源码摘要和测试判据需重新产生对应 proof；失败不覆盖旧成品。报告复用、适配、新增、排除、未知和下一恢复入口。具体原生步骤取决于所安装增强 reverse 版本，安装器本身不实现产品追版算法。

REA bundle、原 case 与 Spec Kit 的规格/任务/测试保存在成果项目中，工具仓库只读。Converged、退出 0、文件存在或静态 `verify` 通过都不能证明任意行为等价；实际原版/本方运行、错误变体检出、独立隔离构建、宿主资源加载和对话触发分别验收。没有设备/provider/账号或隔离环境时保持未验证，不编造闭环。
